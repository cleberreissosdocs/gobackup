APRESENTAÇÃO — GOBACKUP (versão curta)
Texto para fala. Cerca de 5 minutos.
Versão longa, com mais detalhe técnico: apresentacao-gobackup-completa.txt


-----------------------------------------------------------------------
1. O PROBLEMA (1 min 30)
-----------------------------------------------------------------------

Boa tarde. Vou falar do GoBackup, o sistema de backup que desenvolvi
para os nossos servidores.

Começo pelo problema, que a gente viveu durante anos.

Cada servidor tinha seu script de backup, e cada script mandava um
e-mail ao terminar. Eram dezenas de e-mails por dia. Todo dia alguém
abria um por um para saber se aquele backup tinha concluído ou morrido
no meio.

[PAUSA]

Dois defeitos nisso.

O primeiro: conferir dezenas de e-mails iguais é tarefa que o cérebro
aprende a não fazer. Na primeira semana você lê todos. No segundo mês,
eles viram barulho e vão para uma pasta.

O segundo é pior. É o e-mail que NÃO chega. Script quebrado, servidor
desligado, tarefa que nunca iniciou — não chega aviso nenhum. E ausência
de e-mail é igualzinha a uma caixa de entrada tranquila. O sinal mais
grave que existe fica indistinguível de um dia normal.

Era preciso notar uma ausência, no meio de dezenas de presenças, todo
dia. Isso não é disciplina. É sorte.


-----------------------------------------------------------------------
2. O QUE É (1 min 30)
-----------------------------------------------------------------------

O GoBackup inverte essa lógica. Em vez de dezenas de avisos que você
confere, uma tela só, que responde a qualquer momento: todos os meus
servidores estão protegidos agora?

São duas partes. Um agente, instalado em cada servidor, que faz o
trabalho — copia arquivos e extrai bancos de dados. E um painel central,
hospedado fora desses servidores, que enxerga todos ao mesmo tempo.

Fica fora de propósito: painel hospedado na máquina que caiu não serve
para avisar que a máquina caiu.

[TELA: painel]

Uma decisão de arquitetura vale citar, porque é ela que torna o sistema
instalável em qualquer lugar: o agente sempre inicia a conexão com o
painel. O painel nunca procura o agente.

Isso significa que não é preciso abrir nenhuma porta no servidor
protegido. Funciona atrás de firewall, atrás de NAT, em rede de cliente.
Instalar é rodar um instalador e informar o endereço do painel — não é
um projeto de infraestrutura a cada servidor.

E o silêncio deixou de ser ambíguo: quem para de reportar aparece
vermelho em segundos, sozinho, sem ninguém procurar.


-----------------------------------------------------------------------
3. UM CASO REAL (1 min 30)
-----------------------------------------------------------------------

Um exemplo de por que um backup falha na prática.

Num servidor Windows havia um backup que lia uma pasta de outro servidor
da rede, mapeada como unidade Z:. Funcionava quando o técnico testava na
mão. O backup automático falhava sempre, dizendo que o caminho não
existia.

[PAUSA]

A causa: o agente roda como serviço do Windows, e unidade mapeada não
existe para um serviço — ela pertence à sessão de quem fez login. O
técnico enxergava o Z: porque estava logado. O serviço, não.

O mesmo caminho, na mesma máquina, funcionando para uma conta e
inexistente para a outra. Hoje o agente acessa a pasta de rede com
credencial própria, guardada cifrada. Resultado medido em produção: nove
gigabytes e dezoito mil arquivos copiados, sem ninguém logado.

É esse o ponto. Backup não falha por falta de algoritmo de cópia. Falha
em permissão, sessão, credencial — e é aí que o sistema foi endurecido.


-----------------------------------------------------------------------
4. ONDE ESTÁ E O QUE FALTA (45 s)
-----------------------------------------------------------------------

O sistema está em produção, com agentes em Linux e em Windows Server
monitorados na mesma tela, backup de arquivos e dos principais bancos de
dados, e agendamento automático nas duas plataformas.

O que ainda não existe, e prefiro dizer antes que perguntem: teste
automatizado de restauração. O sistema registra tamanho e quantidade de
arquivos de cada execução, o que já denuncia uma cópia vazia, mas não
verifica que o backup restaura. É o próximo passo.


-----------------------------------------------------------------------
5. FECHAMENTO (30 s)
-----------------------------------------------------------------------

Resumindo: antes, a resposta sobre os backups vinha em dezenas de
e-mails que alguém precisava conferir — e o problema mais grave chegava
como silêncio.

Hoje vem de uma tela só, e o silêncio tem cor.

O backup em si é a parte fácil. O difícil é saber, todo dia, que ele
continua acontecendo.

Obrigado.


=======================================================================
SE PERGUNTAREM
=======================================================================

"Por que não uma solução de mercado?"
   Cobram por agente e usam as mesmas ferramentas por baixo. O que se
   compra é o painel — e esse foi feito sob medida para a nossa
   operação. Servidor novo custa o tempo de rodar um instalador.

"E se o painel cair?"
   Os backups continuam. O agente é autônomo, tem seu próprio banco e
   sua própria tela. Cai a visibilidade, não a proteção.

"Como sabem que o backup presta?"
   Hoje, pelo tamanho e quantidade de arquivos de cada execução, que
   denunciam uma cópia vazia. Restauração automatizada é o próximo
   passo — backup que nunca foi restaurado é uma suposição.

"Quanto tempo para instalar num servidor novo?"
   Minutos. Instalador gráfico no Windows, script no Linux.

"Aguenta quantos servidores?"
   O agente trabalha sozinho e só reporta o resultado, então o painel
   não é gargalo de processamento.
